# Tại sao cần dùng hàm? (Tư duy DRY và tái sử dụng code)

## 1. Mục Tiêu Bài Học

- Hiểu bản chất: nguyên lý **DRY (Don't Repeat Yourself — Đừng Lặp Lại Chính Mình)** là gì, và vì sao nó là một trong những nguyên tắc quan trọng nhất của lập trình.
- Nhận diện được vấn đề: code bị lặp lại nhiều lần không chỉ dài dòng, mà còn tiềm ẩn nguy cơ lỗi nghiêm trọng khi cần sửa đổi.
- Ứng dụng được tư duy hàm để gom logic lặp lại vào một nơi duy nhất, tái sử dụng nhiều lần.
- Thấy rõ lợi ích thực tế: code dễ đọc hơn, dễ sửa hơn, và an toàn hơn trước lỗi con người.
- Quan sát việc đổi công thức ở code chép-dán và ở code dùng hàm bằng hoạt động mô phỏng.

## 2. Giới Thiệu

Hãy tưởng tượng bạn cần viết chương trình tính diện tích cho 10 hình chữ nhật khác nhau. Nếu mỗi lần tính bạn đều gõ lại công thức `dai * rong`, bạn sẽ có 10 đoạn code gần như giống hệt nhau, chỉ khác mỗi con số đầu vào.

Vấn đề thực sự xuất hiện khi có thay đổi: nếu một ngày nào đó công thức tính cần điều chỉnh (ví dụ thêm hệ số quy đổi đơn vị), bạn sẽ phải tìm và sửa đúng cả 10 chỗ đó — chỉ cần bỏ sót một chỗ, chương trình sẽ cho ra kết quả sai mà không hề có bất kỳ cảnh báo nào. Đây chính là lúc **Hàm (Function)** trở thành công cụ cứu cánh: gom toàn bộ logic tính toán vào **một nơi duy nhất**, rồi gọi lại nó bao nhiêu lần tùy thích — sửa một chỗ, mọi nơi sử dụng đều tự động được cập nhật theo.

## 3. Khái Niệm

- **Hàm (Function)**: một khối code được đặt tên, đóng gói một đoạn logic cụ thể, có thể được **gọi lại (call)** nhiều lần từ nhiều nơi khác nhau trong chương trình mà không cần viết lại toàn bộ logic đó.
- **DRY (Don't Repeat Yourself)**: nguyên lý lập trình nói rằng mỗi đoạn logic quan trọng chỉ nên được viết (định nghĩa) đúng **một lần duy nhất** trong toàn bộ chương trình.
- **Tái sử dụng code (Code Reuse)**: khả năng dùng lại cùng một đoạn logic ở nhiều nơi khác nhau, thay vì sao chép-dán (copy-paste) lặp đi lặp lại.
- **Lỗi đồng bộ hóa (Synchronization bug)**: lỗi xảy ra khi có nhiều bản sao của cùng một logic, nhưng khi sửa đổi, người viết code lại quên cập nhật đầy đủ ở tất cả các bản sao đó.

## 4. Giải Thích

### 4.1. Vấn Đề Của Việc Lặp Lại Code

Khi cùng một logic được viết đi viết lại nhiều lần, chương trình gặp phải ba vấn đề chính:

- **Dài dòng, khó đọc**: càng nhiều đoạn code giống nhau, người đọc càng khó nắm bắt tổng thể chương trình đang làm gì.
- **Khó bảo trì**: khi cần thay đổi logic, phải tìm và sửa ở **tất cả** những nơi đã sao chép — dễ bỏ sót.
- **Nguy cơ lỗi đồng bộ hóa**: nếu quên sửa dù chỉ một chỗ trong số nhiều bản sao, chương trình sẽ có những phần hoạt động không nhất quán với nhau — đây là loại lỗi cực kỳ khó phát hiện, vì mỗi đoạn code riêng lẻ vẫn "trông có vẻ đúng".

### 4.2. Giải Pháp: Gom Logic Vào Một Hàm Duy Nhất

Thay vì lặp lại công thức tính toán ở nhiều nơi, ta viết công thức đó **đúng một lần** bên trong một hàm, rồi gọi hàm đó ở bất cứ đâu cần dùng đến. Khi cần sửa logic, chỉ cần sửa đúng bên trong hàm — mọi nơi gọi đến hàm đó sẽ tự động nhận được kết quả đã cập nhật, không cần sửa tay từng chỗ.

## 5. Ví Dụ

Toàn bộ output dưới đây đã được biên dịch và chạy thử thực tế để đảm bảo tính chính xác.

### Ví dụ 1: Không dùng hàm — lặp lại code tính diện tích 3 lần (Mục tiêu: nhận diện vấn đề lặp code)

```cpp
#include <iostream>
using namespace std;

int main() {
    int dai1 = 5, rong1 = 3;
    int dienTich1 = dai1 * rong1;
    cout << "Dien tich hinh 1: " << dienTich1 << endl;

    int dai2 = 8, rong2 = 4;
    int dienTich2 = dai2 * rong2;
    cout << "Dien tich hinh 2: " << dienTich2 << endl;

    int dai3 = 10, rong3 = 6;
    int dienTich3 = dai3 * rong3;
    cout << "Dien tich hinh 3: " << dienTich3 << endl;
    return 0;
}
```

**Output đã kiểm chứng:**

```
Dien tich hinh 1: 15
Dien tich hinh 2: 32
Dien tich hinh 3: 60
```

Công thức `dai * rong` được viết lại đúng 3 lần — với 3 hình thì còn chấp nhận được, nhưng nếu là 100 hình, đoạn code này sẽ trở nên khổng lồ và cực kỳ khó quản lý.

### Ví dụ 2: Dùng hàm — cùng bài toán, gọn gàng hơn hẳn (Mục tiêu: thấy giải pháp tái sử dụng code)

```cpp
#include <iostream>
using namespace std;

int tinhDienTich(int dai, int rong) {
    return dai * rong;
}

int main() {
    cout << "Dien tich hinh 1: " << tinhDienTich(5, 3) << endl;
    cout << "Dien tich hinh 2: " << tinhDienTich(8, 4) << endl;
    cout << "Dien tich hinh 3: " << tinhDienTich(10, 6) << endl;
    return 0;
}
```

**Output đã kiểm chứng — giống hệt Ví dụ 1:**

```
Dien tich hinh 1: 15
Dien tich hinh 2: 32
Dien tich hinh 3: 60
```

Công thức tính toán (`dai * rong`) giờ đây chỉ xuất hiện đúng **một lần duy nhất** — bên trong hàm `tinhDienTich`. Dù gọi hàm này bao nhiêu lần với bao nhiêu bộ số liệu khác nhau, logic tính toán vẫn chỉ được viết một chỗ.

### Ví dụ 3: Minh chứng lỗi thực tế — quên cập nhật khi copy-paste code (Mục tiêu: thấy rõ hậu quả của việc không tuân theo DRY)

Giả sử một ngày, yêu cầu thay đổi: mọi hóa đơn cần cộng thêm 5% thuế. Với code đã copy-paste 3 lần, người viết code sửa được 2 chỗ nhưng **lỡ quên** chỗ thứ 2:

```cpp
#include <iostream>
using namespace std;

int main() {
    double hoaDon1 = 100000;
    double tongTien1 = hoaDon1 * 1.05;      // Đã sửa: có thuế
    cout << "Hoa don 1 (co thue): " << tongTien1 << endl;

    double hoaDon2 = 200000;
    double tongTien2 = hoaDon2;             // LỖI: Quên nhân thêm thuế ở đây!
    cout << "Hoa don 2 (QUEN thue - SAI): " << tongTien2 << endl;

    double hoaDon3 = 150000;
    double tongTien3 = hoaDon3 * 1.05;      // Đã sửa: có thuế
    cout << "Hoa don 3 (co thue): " << tongTien3 << endl;
    return 0;
}
```

**Output đã kiểm chứng — hóa đơn 2 bị sai do quên cập nhật:**

```
Hoa don 1 (co thue): 105000
Hoa don 2 (QUEN thue - SAI): 200000
Hoa don 3 (co thue): 157500
```

Hóa đơn 2 đáng lẽ phải là `210000` (200000 × 1.05), nhưng vì code bị sao chép thủ công và người viết quên cập nhật đúng một chỗ, kết quả bị sai lệch mà **không hề có bất kỳ lỗi biên dịch hay cảnh báo nào** — đây chính là "lỗi đồng bộ hóa" nguy hiểm đã nói ở phần lý thuyết.

### Ví dụ 4: Sửa bằng hàm — chỉ cần sửa đúng 1 chỗ, mọi nơi tự động đúng (Mục tiêu: thấy lợi ích thực tế của tư duy DRY)

```cpp
#include <iostream>
using namespace std;

double tinhTongTienCoThue(double hoaDon) {
    return hoaDon * 1.05;    // Muốn đổi mức thuế, chỉ cần sửa đúng dòng này
}

int main() {
    cout << "Hoa don 1 (co thue): " << tinhTongTienCoThue(100000) << endl;
    cout << "Hoa don 2 (co thue): " << tinhTongTienCoThue(200000) << endl;
    cout << "Hoa don 3 (co thue): " << tinhTongTienCoThue(150000) << endl;
    return 0;
}
```

**Output đã kiểm chứng — cả 3 hóa đơn đều tính đúng thuế, không sót chỗ nào:**

```
Hoa don 1 (co thue): 105000
Hoa don 2 (co thue): 210000
Hoa don 3 (co thue): 157500
```

Khác hẳn với Ví dụ 3, ở đây không có nguy cơ "quên cập nhật một chỗ" — vì công thức tính thuế chỉ tồn tại ở đúng một vị trí duy nhất bên trong hàm `tinhTongTienCoThue`. Đây chính là giá trị cốt lõi mà nguyên lý DRY mang lại.

*(Lưu ý: với tiền tệ thực tế, người ta thường lưu số nguyên (đơn vị đồng) thay vì số thực, vì số thực có thể có sai số làm tròn rất nhỏ.)*

### Ví dụ 5: Tái sử dụng hàm trong vòng lặp — kiểm tra số nguyên tố (Mục tiêu: ứng dụng hàm với logic phức tạp hơn)

```cpp
#include <iostream>
using namespace std;

bool laSoNguyenTo(int n) {
    if (n < 2) return false;
    for (int i = 2; i * i <= n; i++) {
        if (n % i == 0) return false;
    }
    return true;
}

int main() {
    int cacSo[6] = {7, 10, 13, 15, 2, 21};
    for (int i = 0; i < 6; i++) {
        int so = cacSo[i];
        cout << so << ": ";
        if (laSoNguyenTo(so))
            cout << "nguyen to\n";
        else
            cout << "khong phai\n";
    }
    return 0;
}
```

**Output đã kiểm chứng:**

```
7: nguyen to
10: khong phai
13: nguyen to
15: khong phai
2: nguyen to
21: khong phai
```

Đây là minh chứng cho việc hàm không chỉ giúp tránh lặp code với những công thức đơn giản, mà còn cực kỳ hữu ích với những logic phức tạp hơn (như thuật toán kiểm tra số nguyên tố) — logic phức tạp chỉ cần viết đúng một lần, sau đó có thể gọi lại bên trong vòng lặp để kiểm tra hàng loạt giá trị khác nhau một cách gọn gàng. Điều kiện `i * i <= n` giúp hàm chỉ thử các số tới căn bậc hai của `n`, không cần thử hết.

### Xem hàm tiết kiệm công sửa như thế nào, từng bước

Mô phỏng dưới đây cho hai cách viết cùng đối mặt với yêu cầu "cộng thuế 5%". Bấm **Bước tiếp** để chạy từng bước và để ý những điều mà chữ khó diễn tả:

- Tab **Đổi công thức: copy-paste và hàm**: hai cột chạy song song, có bảng kết quả và bộ đếm "chỗ phải sửa" ở cuối. Cột trái phải sửa 3 chỗ và ô của hóa đơn 2 tô đỏ vì bị sót; cột phải chỉ sửa 1 chỗ và ba lời gọi cùng sáng lên vì cùng nối vào một hàm.
- Tab **Dùng lại hàm trong vòng lặp**: mỗi số của mảng đi qua hàm `laSoNguyenTo` như qua một trạm kiểm tra, ô của số đó chuyển xanh (nguyên tố) hoặc đỏ (không phải), còn hộp bên dưới cho thấy giá trị truyền vào và giá trị trả về.

## 6. Phần Chú Ý Và Lỗi Hay Gặp

- **Copy-paste code thay vì viết hàm khi thấy logic lặp lại**: đây chính là thói quen dẫn đến lỗi đồng bộ hóa đã minh chứng ở Ví dụ 3. Ngay khi nhận thấy mình đang gõ lại một đoạn logic đã viết trước đó, hãy dừng lại và cân nhắc gom nó thành một hàm.
- **Nghĩ rằng viết hàm chỉ hữu ích khi logic phức tạp**: trên thực tế, ngay cả những công thức đơn giản như tính diện tích (Ví dụ 1, 2) cũng nên được gom thành hàm nếu được dùng lại nhiều lần — lợi ích không chỉ nằm ở độ phức tạp của logic, mà ở số lần logic đó được tái sử dụng.
- **Không nhận ra dấu hiệu cần viết hàm**: một quy tắc kinh nghiệm phổ biến là "nếu bạn viết cùng một đoạn code từ 2-3 lần trở lên, đó là dấu hiệu rõ ràng cần chuyển nó thành một hàm".
- **Chỉ sửa được một phần khi phát hiện lỗi trong code lặp lại**: khi phát hiện lỗi trong logic bị sao chép nhiều lần, người viết code thường phải rà soát thủ công từng nơi xuất hiện của nó — nguy cơ bỏ sót luôn hiện hữu, đặc biệt với chương trình lớn có hàng trăm, hàng nghìn dòng code.
- **Đánh giá thấp lợi ích của việc tái sử dụng hàm giữa các dự án khác nhau**: một hàm được viết tốt (như `laSoNguyenTo` ở Ví dụ 5) không chỉ hữu ích trong chương trình hiện tại, mà còn có thể được mang sang tái sử dụng ở các bài toán hoặc dự án khác trong tương lai mà không cần viết lại từ đầu.
