# Tính Đóng Gói: Tại Sao Cần Getter & Setter?

## 1. Mục Tiêu Bài Học

- Hiểu bản chất: **Tính đóng gói (Encapsulation)** là gì — sự kết hợp giữa `private` (bảo vệ dữ liệu) và các phương thức `public` có kiểm soát (Getter/Setter) để truy cập dữ liệu đó.
- Nắm vững khái niệm: **Getter** (phương thức lấy giá trị) và **Setter** (phương thức gán giá trị) là gì, cùng quy ước đặt tên phổ biến (`getX()`, `setX()`).
- Ứng dụng được vào việc viết Setter có kiểm tra tính hợp lệ (validation), và thuộc tính "chỉ đọc" (chỉ có Getter, không có Setter).
- Hiểu được lợi ích cốt lõi: có thể thay đổi logic kiểm tra bên trong lớp mà **không ảnh hưởng** đến code đã gọi Getter/Setter ở nơi khác.

## 2. Giới Thiệu

Ở bài trước, bạn đã học cách dùng `private` để "khóa" thuộc tính, và viết các phương thức riêng để gán/đọc giá trị một cách có kiểm soát. Bài này sẽ chính thức đặt tên cho kỹ thuật đó — đây chính là **Tính đóng gói (Encapsulation)**, một trong bốn trụ cột quan trọng nhất của lập trình hướng đối tượng.

Ý tưởng cốt lõi rất đơn giản: hãy tưởng tượng một chiếc hộp đen — bên trong chứa dữ liệu quan trọng (`private`), nhưng bên ngoài chỉ có vài cái nút bấm được thiết kế sẵn để tương tác với nó (`public` — chính là Getter và Setter). Người dùng bên ngoài không cần biết (và không được phép biết) cơ chế bên trong hoạt động ra sao — họ chỉ cần bấm đúng nút là nhận được kết quả mong muốn, một cách an toàn và có kiểm soát.

## 3. Khái Niệm

- **Tính đóng gói (Encapsulation)**: nguyên tắc thiết kế kết hợp việc ẩn giấu dữ liệu (`private`) với việc cung cấp các phương thức `public` có kiểm soát để tương tác với dữ liệu đó.
- **Getter**: một phương thức `public`, có nhiệm vụ **trả về** giá trị của một thuộc tính `private` — quy ước đặt tên phổ biến là `getTênThuộcTính()`.
- **Setter**: một phương thức `public`, có nhiệm vụ **gán** giá trị mới cho một thuộc tính `private` — thường kèm theo logic kiểm tra tính hợp lệ trước khi thực sự gán. Quy ước đặt tên phổ biến là `setTênThuộcTính(giá_trị)`.
- **Thuộc tính chỉ đọc (Read-only)**: thuộc tính chỉ có Getter mà không có Setter tương ứng — cho phép đọc giá trị nhưng không cho phép thay đổi từ bên ngoài.

## 4. Giải Thích

### 4.1. Cấu Trúc Cơ Bản Của Getter Và Setter

```cpp
class HocSinh {
private:
    int tuoi;

public:
    void setTuoi(int t) {        // SETTER - gán giá trị, có thể kiểm tra hợp lệ
        tuoi = t;
    }
    int getTuoi() {              // GETTER - chỉ đơn giản trả về giá trị
        return tuoi;
    }
};
```

### 4.2. Setter Với Logic Kiểm Tra Tính Hợp Lệ

Điểm mạnh thực sự của Setter là khả năng **kiểm tra** trước khi gán — nếu giá trị không hợp lệ, Setter có thể từ chối gán, hoặc xử lý theo cách khác, thay vì để dữ liệu sai lọt vào đối tượng.

### 4.3. Thuộc Tính Chỉ Đọc — Không Viết Setter

Nếu một thuộc tính không nên bị thay đổi sau khi đối tượng được tạo ra (ví dụ mã số học sinh), bạn chỉ cần viết Getter cho nó mà **không viết Setter tương ứng** — khi đó, không có cách nào từ bên ngoài có thể thay đổi được giá trị này nữa.

### 4.4. Lợi Ích Cốt Lõi: Linh Hoạt Thay Đổi Logic Bên Trong

Vì mọi tương tác với dữ liệu đều phải đi qua Getter/Setter, bạn hoàn toàn có thể **thay đổi logic bên trong** các phương thức này (thêm điều kiện kiểm tra mới, thay đổi cách tính toán...) mà **không cần sửa** bất kỳ đoạn code nào khác đã gọi đến chúng — đây chính là lợi ích lớn nhất của tính đóng gói.

## 5. Ví Dụ

Các output và thông báo lỗi dưới đây được lấy từ lần biên dịch, chạy thử thực tế (thông báo lỗi theo g++).

### Ví dụ 1: Getter và Setter cơ bản (Mục tiêu: nắm cấu trúc cơ bản nhất)

```cpp
#include <iostream>
#include <string>
using namespace std;

class HocSinh {
private:
    string ten;
    int tuoi;

public:
    void setTen(string t) { ten = t; }
    void setTuoi(int t) {
        if (t > 0 && t < 100) {
            tuoi = t;
        } else {
            cout << "Tuoi khong hop le! Giu nguyen gia tri cu." << endl;
        }
    }
    string getTen() { return ten; }
    int getTuoi() { return tuoi; }
};

int main() {
    HocSinh hs;
    hs.setTen("Nguyen Van An");
    hs.setTuoi(16);

    cout << "Ten: " << hs.getTen() << endl;
    cout << "Tuoi: " << hs.getTuoi() << endl;
    return 0;
}
```

**Output đã kiểm chứng:**

```
Ten: Nguyen Van An
Tuoi: 16
```

### Ví dụ 2: Setter với logic kiểm tra tính hợp lệ (Mục tiêu: thấy rõ giá trị của Setter so với gán trực tiếp)

Dùng lại lớp `HocSinh` ở Ví dụ 1, hàm `main()` bây giờ thử gán cả giá trị đúng lẫn sai:

```cpp
int main() {
    HocSinh hs;
    hs.setTuoi(16);
    cout << "Tuoi ban dau: " << hs.getTuoi() << endl;

    hs.setTuoi(-5);   // Giá trị không hợp lệ
    cout << "Tuoi sau khi thu gan -5: " << hs.getTuoi() << endl;

    hs.setTuoi(200);   // Giá trị không hợp lệ
    cout << "Tuoi sau khi thu gan 200: " << hs.getTuoi() << endl;
    return 0;
}
```

**Output đã kiểm chứng:**

```
Tuoi ban dau: 16
Tuoi khong hop le! Giu nguyen gia tri cu.
Tuoi sau khi thu gan -5: 16
Tuoi khong hop le! Giu nguyen gia tri cu.
Tuoi sau khi thu gan 200: 16
```

Cả hai lần thử gán giá trị vô lý (`-5` và `200`) đều bị Setter từ chối, và `tuoi` vẫn giữ nguyên giá trị hợp lệ trước đó (`16`) — nếu `tuoi` là `public` và được gán trực tiếp, không có cách nào ngăn được những giá trị vô lý này.

### Ví dụ 3: Thuộc tính chỉ đọc — có Getter, không có Setter (Mục tiêu: ứng dụng bảo vệ dữ liệu không nên thay đổi)

```cpp
#include <iostream>
#include <string>
using namespace std;

class HocSinh {
private:
    string maSoHocSinh;   // Không có Setter - không thể đổi sau khi tạo
    string ten;

public:
    HocSinh(string maSo, string tenBanDau) {
        maSoHocSinh = maSo;
        ten = tenBanDau;
    }
    string getMaSoHocSinh() { return maSoHocSinh; }   // CHỈ có Getter
    void setTen(string t) { ten = t; }
    string getTen() { return ten; }
};

int main() {
    HocSinh hs("HS001", "Nguyen Van An");
    cout << "Ma so: " << hs.getMaSoHocSinh() << endl;

    hs.setTen("Nguyen Van An (da doi ten)");
    cout << "Ten sau khi doi: " << hs.getTen() << endl;
    cout << "Ma so van khong doi: " << hs.getMaSoHocSinh() << endl;
    return 0;
}
```

**Output đã kiểm chứng:**

```
Ma so: HS001
Ten sau khi doi: Nguyen Van An (da doi ten)
Ma so van khong doi: HS001
```

`ten` có thể thay đổi qua `setTen()`, nhưng `maSoHocSinh` thì không — vì không hề tồn tại một `setMaSoHocSinh()` nào cả. Nếu thử gọi `hs.setMaSoHocSinh("HS002");`, trình biên dịch sẽ báo lỗi ngay:

```
error: 'class HocSinh' has no member named 'setMaSoHocSinh'; did you mean 'getMaSoHocSinh'?
```

### Ví dụ 4: Lợi ích cốt lõi — thay đổi logic bên trong Setter mà không ảnh hưởng code gọi (Mục tiêu: hiểu giá trị thực sự của tính đóng gói)

```cpp
#include <iostream>
using namespace std;

class TaiKhoan {
private:
    double soDu;
public:
    TaiKhoan() { soDu = 0; }

    void setSoDu(double giaTri) {
        if (giaTri < 0) {
            cout << "Loi: khong the am!" << endl;
            return;
        }
        // MỚI THÊM: giờ còn giới hạn tối đa 1 tỷ (logic thay đổi, cách GỌI HÀM không đổi!)
        if (giaTri > 1000000000) {
            cout << "Loi: vuot qua han muc cho phep!" << endl;
            return;
        }
        soDu = giaTri;
    }
    double getSoDu() { return soDu; }
};

int main() {
    TaiKhoan tk;
    tk.setSoDu(-100);
    tk.setSoDu(2000000000);
    tk.setSoDu(500000);
    cout << "So du cuoi cung: " << tk.getSoDu() << endl;
    return 0;
}
```

**Output đã kiểm chứng:**

```
Loi: khong the am!
Loi: vuot qua han muc cho phep!
So du cuoi cung: 500000
```

Đây là minh chứng quan trọng nhất của bài học: dù bên trong `setSoDu()` đã được bổ sung thêm một quy tắc kiểm tra hoàn toàn mới (giới hạn tối đa 1 tỷ), cách gọi hàm ở `main()` (`tk.setSoDu(...)`) **không hề phải thay đổi gì cả**. Nếu ban đầu `soDu` là `public` và được gán trực tiếp khắp nơi trong chương trình, việc bổ sung quy tắc mới này sẽ buộc phải sửa lại **từng chỗ** đã gán trực tiếp — một công việc rất dễ bỏ sót, giống vấn đề DRY đã học ở phần Hàm.

### Xem Setter và Getter hoạt động từng bước

Mô phỏng dưới đây vẽ mỗi đối tượng thành hai phòng (`private` và `public`), cùng một trạm đèn kiểm tra cho Setter. Bấm **Bước tiếp** để chạy từng dòng code và để ý những điều mà chữ khó diễn tả:

- Tab **setTuoi kiểm tra hợp lệ**: mỗi lần gọi `setTuoi()` có hai đèn `t > 0` và `t < 100`. Với `16` cả hai xanh nên `tuoi` đổi, với `-5` và `200` có một đèn đỏ nên `tuoi` đứng yên ở `16`. Sau mỗi lần, `getTuoi()` cho thấy giá trị hiện tại.
- Tab **Chỉ đọc: maSoHocSinh**: trong phòng `public` chỉ có `getMaSoHocSinh()`, không có cổng set tương ứng. Khi dòng `hs.setMaSoHocSinh("HS002");` chạy, thẻ lỗi hiện ra và ô `maSoHocSinh` chuyển đỏ.
- Tab **Đổi luật Setter, main không đổi**: thêm luật `≤ 1 tỷ` thì hàng đèn có thêm đèn thứ hai, còn các dòng gọi trong `main()` giữ nguyên. Ở bước cuối, bộ đếm so sánh số chỗ phải sửa: 5 chỗ nếu `soDu` là `public`, 1 chỗ nếu dùng Setter. (Để vừa khung code, mô phỏng dùng thông báo lỗi ngắn hơn ví dụ trên.)

## 6. Phần Chú Ý Và Lỗi Hay Gặp

- **Viết Getter/Setter cho mọi thuộc tính một cách máy móc mà không cân nhắc**: không phải thuộc tính nào cũng cần cả Getter lẫn Setter — hãy tự hỏi thuộc tính đó có nên được thay đổi từ bên ngoài hay không (như Ví dụ 3), trước khi quyết định có viết Setter hay không.
- **Setter không có bất kỳ logic kiểm tra nào, chỉ đơn thuần gán giá trị**: nếu Setter chỉ làm mỗi việc `thuocTinh = giaTri;` mà không kiểm tra gì, nó gần như không khác gì để thuộc tính đó `public` — hãy tận dụng Setter để thêm logic bảo vệ dữ liệu như Ví dụ 2 và 4.
- **Quên đặt tên theo quy ước `getX()`/`setX()`**: dù không bắt buộc về mặt kỹ thuật, việc tuân thủ quy ước đặt tên này giúp code dễ đọc và dễ đoán hơn rất nhiều — người đọc code của bạn (kể cả chính bạn sau này) sẽ ngay lập tức hiểu được mục đích của từng phương thức.
- **Không xử lý trường hợp giá trị không hợp lệ trong Setter một cách rõ ràng**: như Ví dụ 2, khi Setter từ chối một giá trị, nên có phản hồi rõ ràng (thông báo lỗi, giữ nguyên giá trị cũ...) thay vì âm thầm bỏ qua mà không cho người gọi biết chuyện gì đã xảy ra.
- **Quên gán giá trị đầu cho thuộc tính**: nếu Setter từ chối ngay lần gán đầu tiên mà lớp không có constructor, thuộc tính vẫn là giá trị rác. Hãy khởi tạo giá trị hợp lệ trong constructor, như `TaiKhoan() { soDu = 0; }` ở Ví dụ 4.
- **Đánh giá thấp lợi ích lâu dài của tính đóng gói**: lợi ích thực sự của Getter/Setter không nằm ở những chương trình nhỏ, đơn giản — nó thể hiện rõ nhất khi chương trình phát triển lớn hơn, có nhiều nơi trong code cùng sử dụng một lớp, và bạn cần thay đổi logic nội bộ mà không muốn "đập đi xây lại" toàn bộ những nơi đã sử dụng lớp đó (như đã minh chứng ở Ví dụ 4).
